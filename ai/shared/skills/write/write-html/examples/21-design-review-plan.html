Design review, revision 3

Acme Ledger webhooks, from spec to production

Customers want their own systems told the moment something changes in Ledger, instead of polling the API every minute. This page shows what we are building, how one event travels through it, what already exists, and the order the work lands in.

Not approved for implementation yet Owner: Jordan Reyes Updated 2026-03-14 Reference build a1b2c3d
The plan in short
  1. One new service, webhook-service. A customer registers an HTTPS URL, picks event types, and Ledger POSTs a signed event to that URL whenever one of those things happens in their workspace.
  2. Most of it exists. The event bus and the public object shapes are finished on main. The service itself is written and tested as a prototype, but it arrived as one pull request too large to review.
  3. The plan carries that code into main as 12 small PRs. Each one is checked live in the lab before it merges and on DEV after. Three reference receivers are tested as soon as signing works.
  4. The finish line for this plan is dormant production: everything deployed, deliveries off. Turning deliveries on is a separate approval.
What we are building

Ledger calls the customer, not the other way round

A webhook is an HTTP POST we send to a URL the customer owns. Our service reads internal events on one side and sends public, signed payloads on the other. It never sends an internal event as-is, and it never decides who may see what.

18 event types

One catalog for everyone

Invoices, payments, customers, reports, subscriptions and audit. A customer can subscribe only to types their role is allowed to read.

1 workspace per endpoint

Events never cross workspaces

An endpoint belongs to one workspace and receives that workspace's events only. The check runs before a payload is built.

≥ 1 delivery per event

At least once, never zero

Every event is retried until the endpoint answers 2xx or the retry window closes. Each payload carries an event id to deduplicate on.

10 s per attempt

Everything is bounded

256 KiB per payload, a 10-second deadline per attempt, 50 deliveries a second per endpoint. One slow endpoint cannot hold up another.

72 h of retries

Outages are survivable

Failed deliveries back off from 30 seconds to 6 hours. After 72 hours of failure the endpoint is disabled and its events are kept 7 days for replay.

24 h secret overlap

Rotating a secret breaks nothing

Each endpoint has its own signing secret. On rotation both secrets sign for 24 hours, so the customer can switch without a gap.

How it works

One event, start to finish

The service has two jobs: prove the customer owns the URL, then turn each internal event into a public payload the customer can trust. Follow the two colors to see what crosses to the customer and what never does.

  1. Subscribe, once per endpoint
  2. The customer's app calls POST /v1/webhooks with an HTTPS URL and the event types it wants.
  3. The service sends a one-time challenge to that URL. Nothing is delivered until it is answered.
  4. The app echoes the challenge back, proving it controls the URL.
  5. The service returns a signing secret, shown once. The customer stores it to check every delivery.
  6. Every event
  7. A backend publishes an internal event to the bus, for example invoice.paid.
  8. The service reads it, drops it if the event id was already handled, and finds the endpoints subscribed to that type in that workspace.
  9. The service fetches the invoice's public view, the same shape GET /v1/invoices/{id} returns.
  10. The backend applies the endpoint owner's permissions and returns public fields only.
  11. The service signs the timestamp and body with the endpoint's secret and POSTs it.
  12. Any 2xx within 10 seconds counts as delivered. Anything else is retried with backoff.

Signed payload the customer receives it

  • The public API's shape for that object, plus an event id, type and timestamp.
  • Signed with HMAC over the timestamp and body; deliveries older than 5 minutes should be rejected by the receiver.
  • Identical on every retry, so the event id is a safe key to deduplicate on.

Internal event never leaves Acme

  • Published by the backend that owns the object, onto the internal bus.
  • Carries internal ids and fields the public API does not expose.
  • Used only as a trigger; the payload is always rebuilt from the public view.

One limit to know: delivery is at least once and not ordered across event types, so a customer can see payment.succeeded before invoice.paid. The customer guide says to treat each event as a hint and read the object if order matters.

Where a delivery can stop

Each event passes the same checks in a fixed order, cheapest first. Pick a situation to see which step stops it and how the delivery ends.

What happens when…
  1. Read from the busdeduplicated by event id
  2. Match subscriptionsendpoint wants this type and is enabled
  3. Build the payloadpublic fields only, at most 256 KiB
  4. Endpoint rate limit50 deliveries a second per endpoint
  5. Sign and sendHMAC over timestamp and body
  6. Customer answersany 2xx within 10 seconds
The delivery ends as

Every attempt, successful or not, appears in the endpoint's delivery log in the dashboard for 7 days, with the status code and timing but never the body.

What the start is waiting on

The spec carries three flags in its header. By its own rules, production code merges only after the second one says yes.

System design approvedno

Needs Dev, SRE and QA. Dev approved an earlier revision. SRE has commented.

Approved for implementationno

Needs the first flag, and sign-off on the egress plan.

Contract frozenno

Expected. PR 10 sets it, before the evidence pack is signed.

  1. Reviews of the current text. Priya approved and Sam commented at commit 4e5f6a7. Since then the spec gained thin events and the receiver checkpoint.
  2. SRE sign-off. Sam confirmed the retry budget but has not signed off. New for SRE: outbound calls to customer URLs need an egress path that cannot reach internal addresses.
  3. A full trace of the acceptance criteria. The spec has 120 and wants evidence for each. There is no complete map from criterion to PR and test yet.
  4. A named QA reviewer for the DEV evidence pack, independent of the author.

Risks worth watching

  • One slow customer backs up everyone. Per-endpoint queues and the 10-second deadline exist for this; the staging load test proves it.
  • Receivers skip the signature check. The SDK helper makes it one line, and the guide leads with it.
  • A customer URL points inside our network. Endpoints resolving to private addresses are refused at registration and again at send time.
  • Carried code gets waved through because it has tests. Each PR lists what is unchanged so it still gets read.

Left out on purpose

  • Filters beyond event type.
  • Ordering across event types.
  • Plain-HTTP endpoints.
  • Customer-chosen retry schedules.
Decisions

Decided on 2026-03-14, and what still waits on others

Numbers match the design review. Green is the decision. Amber is what still has to come from someone else; where there is no amber line, nothing is waiting.

  1. Reuse PR #42's code in small PRs, or write it again?Morgan agreed to reuse, as long as each layer is reviewed again.Decided: reuse it, one layer per PR
  2. How long do we keep retrying a failing endpoint?24 hours misses a long weekend outage; a week fills the queue with events nobody will read.Decided: 72 hours of retries, then disable the endpoint and keep its events 7 days for replayWaiting on: Sam, to confirm queue storage for the worst case
  3. What happens when an object is too big for one payload?Some reports are several megabytes.Decided: send a thin event with the id, type and an API link; the receiver fetches the rest
  4. One shared delivery queue, or one per endpoint?A shared queue is simpler, but one slow endpoint delays everyone behind it.Decided: one queue per endpoint, capped at 50 deliveries a second each
  5. Who does the gated work that had no owner?Reference receivers; load testing; dashboards, alerts and probes; the security review.Decided: Jordan owns the reference receiversWaiting on: SRE to name owners for load testing and monitoring, and Security for the review
